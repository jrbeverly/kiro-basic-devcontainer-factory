# WAF IP set allowlist distributed by CloudFormation StackSet

## Goal

Prove that a CloudFormation stack can take a list of CIDRs from an SSM StringList
parameter and, from that alone, provision a WAF IP set and an SSM parameter naming
it, at a path a consumer can predict without looking the stack up.

Terraform provisions the source StringList parameter and the stack that consumes
it.

## Context

- The arrangement this is heading towards is one parameter held in a central
  account and read by StackSet deployments everywhere, so the allowlist is
  maintained once and appears in every account. What is being proved here is the
  deployment concept, not that arrangement.
- The stack is the unit a StackSet would deploy. Anything it needs has to arrive
  as a CloudFormation parameter or be derivable inside the template; it cannot
  reach back to something only Terraform knows.
- Consumers find the IP set through the predictable SSM path rather than a stack
  output, so nothing has to know which stack produced it.

## Constraints

- Every entry is CIDR notation. A single address is written `/32` or `/31`, never
  bare.
- The CIDR list is generated in Terraform from a count, not read from a file. A
  file has to be mocked and then mocked again at every size; a count is the size.
- Two or three entries prove the flow works. Two to three hundred prove it
  configures, and the experiment has to reach that scale rather than assume it.
- Terraform is the only provisioning mechanism for the source parameter and the
  stack. Inside the stack, CloudFormation is; the template declares its own
  resources and is not templated by Terraform.
- Do not run `terraform apply`, and do not run any command that calls AWS. Work
  stops at `terraform fmt`, `terraform init -backend=false`, and
  `terraform validate`. The end-to-end check is written and reviewed but never
  executed here.

## Open questions

- Whether the template can declare an `AWS::SSM::Parameter::Value<List<String>>`
  parameter and hand its values straight to the IP set's addresses, or whether the
  list has to be transformed on the way. This is the integration the whole
  experiment exists to answer, so confirm it against the resource specification
  rather than assuming it.
- Whether the parameter survives three hundred CIDRs. A standard-tier SSM
  parameter holds four thousand characters and three hundred CIDRs sit near that
  line, so the scale story may be what discovers the advanced tier is needed.
  Record the size at which it breaks.
- Whether CloudFormation resolves an SSM parameter once at deploy time or follows
  it afterwards. If it resolves once, a change to the central list reaches an
  account only when its stack is updated, which decides whether the arrangement
  above works at all. Record the finding; do not design around either answer yet.
- Which IP set scope the experiment uses, and whether that pins the region.

## Stories

### 1. Source parameter

Terraform creates the SSM StringList parameter holding the generated CIDR list,
with the count of entries as the thing that varies.

### 2. Deployable stack

A Terraform-managed CloudFormation stack whose template declares nothing but one
SSM parameter with a fixed value, proving the stack deploys and stays managed.

### 3. IP set in the stack

Add a WAF IP set to the template, with fixed addresses.

### 4. Published parameter

Add the SSM parameter that will carry the IP set's identity, still with a fixed
value.

### 5. Predictable path

That parameter names the IP set at a path a consumer can construct without knowing
which stack produced it.

### 6. Integration

Replace the fixed values. The stack takes the StringList parameter it receives and
uses it for both the IP set's addresses and the parameter it publishes.

### 7. End-to-end check and scale

A check that proves the flow, and a second example at the two-to-three-hundred
CIDR scale that shows what the size does to it.
