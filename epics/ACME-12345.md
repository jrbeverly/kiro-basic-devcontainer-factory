# No-code MP4 transcription through SSM Automation

## Goal

Someone uploads an MP4 to a bucket and the transcription appears beside it. S3
sends the object-created event to EventBridge, EventBridge starts an SSM
Automation runbook, and the runbook drives Amazon Transcribe to completion.

Nothing is written that has to be run, deployed, or maintained. There is no
Lambda, no container, no build, and no integration for anyone to do afterwards.

## Context

- The only interface is the bucket. There is no API, no UI, and no caller.
- The runbook is the whole orchestration. Every step is an Automation action that
  calls an AWS API; the runbook replaces the code that would otherwise sit in a
  Lambda.
- Transcribe is asynchronous, so the flow is start-then-wait rather than a single
  call.

## Constraints

- No application code anywhere. No Lambda, no container image, no build step, and
  no `aws:executeScript`: an Automation step that runs Python or PowerShell is
  code, and it is the thing this is trying to avoid.
- Terraform is the only provisioning mechanism. No console steps and no scripts
  that create infrastructure.
- The transcription lands beside the source object, under the source key with
  `.vtt` and `.json` appended, so `talk.mp4` produces `talk.mp4.vtt` and
  `talk.mp4.json`.
- Only MP4 objects start a transcription. Anything else the flow sees is ignored,
  including the transcription output the flow writes back into the same bucket.
- No custom vocabulary. If Transcribe turns out to require one, mock the smallest
  one that satisfies it and record why it was needed.
- Do not run `terraform apply`, and do not run any command that calls AWS. Work
  stops at `terraform fmt`, `terraform init -backend=false`, and
  `terraform validate`. The scripts and the end-to-end check are written and
  reviewed but never executed here.

## Open questions

- Whether the runbook can read the uploaded object's metadata or tags without
  code. This is an attempt, not a requirement: if no Automation action reaches it,
  record what was tried and leave it out rather than reaching for a script.
- Whether Transcribe writes to a chosen key or dictates its own output location.
  If it dictates one, moving the result into place is another API call in the
  runbook, and the finding is worth recording before adding the step.
- Whether EventBridge can filter to MP4 objects on its own, or whether the runbook
  has to decide, which matters because the flow writes into the bucket it watches.

## Stories

### 1. Media bucket and event delivery

The bucket that receives uploads, with its object-created events reaching
EventBridge.

### 2. Triggered runbook

An SSM Automation runbook that an upload starts through EventBridge. It does
nothing yet; the point is that the path from upload to execution works.

### 3. Invocation probe

A helper that answers whether an upload actually started an execution, and what
that execution did, so the rest of the work can be observed as it is built.

### 4. Sample media

A small MP4 that is known-valid input, either committed or fetched by a script.
Synthetic speech would be better than silence if it is cheap to produce, but a
known-good file that already exists is worth more than a way to generate one.

### 5. Transcription

The runbook starts a transcription job for the object that triggered it, in place
of doing nothing.

### 6. Completion

The runbook waits for the job to finish and leaves the results beside the source
object.

### 7. Object metadata

Attempt to read the uploaded object's metadata or tags from inside the runbook.
This is the open question above rather than a requirement, and a recorded
negative result closes it.

### 8. End-to-end check

A check that uploads the sample, waits for the flow, and asserts both outputs
appear beside it.
